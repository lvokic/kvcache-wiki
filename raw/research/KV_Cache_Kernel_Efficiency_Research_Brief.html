01 / RESEARCH FOCUS

研究目标已经从生命周期管理转向执行效率

在给定模型质量与内存预算下，降低每个 decode step 的检索、数据访问和 attention 执行成本，同时让持续追加 KV 的更新开销可控。

现在的主线

CPU 上的检索与批量更新；token/page 索引与物理布局；GPU 上的分页或稀疏 attention kernel；CPU–GPU 传输和计算重叠。最终用 TPOT、吞吐、尾延迟、读取字节数和更新成本判断收益。

生命周期只保留为约束

prefix sharing、引用计数、会话恢复和分支隔离仍影响正确性，但不再作为核心贡献。只有测量表明它们阻碍检索、搬运或 kernel 执行时，才纳入设计。

研究状态目前没有确认的 novelty。“graph index + page + CXL”是设计组合，不能单独构成贡献。

02 / START WITH INFERENCE

从 CS336 Lecture 10 进入 KV cache 实现

CS336 Spring 2025 · Lecture 10: Inference 是起点。先理解 prefill/decode、arithmetic intensity、KV cache、continuous batching 和 PagedAttention。Lecture 8 的 DDP 只需保留 all-reduce、通信与计算重叠等概念；scaling laws 可以暂时跳过。

为什么 decode 是主战场

Lecture 10 的核心推导是：prefill 有较大的序列并行度，更容易进入 compute-bound；decode 每步只有少量 query，却需要读取历史 KV，attention 常受内存带宽限制。

FlashAttention 与 sparse page 的关系

FlashAttention 优化完整 attention 的 IO。Top-k page 改变参与计算的历史集合。选中页内部可以精确计算，但对完整历史通常仍是近似。

推荐顺序：Lecture 10 → PagedAttention/vLLM → FlashAttention 的 online softmax → RetrievalAttention / MoBA / IceCache → 具体 kernel 与系统瓶颈。

03 / CRITICAL PATH

把“索引更快”拆成真实执行链

1. 产生 qGPU projection；按层、query head 产生查询。
2. 检索选页CPU 扫描或图搜索；映射、去重与预算选择。
3. 加载 KVDRAM/CXL 读取；gather、DMA 与 staging。
4. AttentionGPU 读取选中页，QK、softmax、PV 与合并。
5. 更新追加新 KV；更新摘要、索引和映射。
端到端速度由关键路径决定。必须分别记录各阶段耗时、CPU 排队、GPU 等待和实际重叠比例；不能默认阶段完全串行，也不能默认它们完全重叠。

CPU / C++ 候选热点

  • 批量 inner product、图遍历和候选扩展。
  • token IDs 到 page IDs 的映射、去重与预算截断。
  • 插入缓冲、centroid 更新与邻接维护。
  • NUMA/CXL 下索引节点和边的局部性。

GPU / CUDA 或 Triton 候选热点

  • 非连续页读取、gather 和分页 attention。
  • 变长候选集合与 GQA 下的重复读取。
  • 局部/远端 partial outputs 的稳定归一化合并。
  • launch、同步和小任务调度开销。

待验证GPU 计算近期 KV 时，CPU 可能搜索旧 KV；多请求也提供流水线机会。但同一层的搜索要先拿到 q。跨层预取通常依赖预测，必须统计误判与修正成本。

不要预设“候选放回 GPU 一定更快”。RetrievalAttention 在 CPU 上直接计算检索部分的 partial attention，只返回小结果，从而避免搬运 K/V。它应当成为 GPU block attention 路径的直接对照。

04 / PAGE GRANULARITY LAB

Page 是分配单位，也是检索和读取成本单位

vLLM 当前配置代码的默认 block size 是 16 tokens；具体模型和 backend 可以采用其他大小。单层、单个 KV head 的一个 B-token page 包含 B 个 K vectors 与 B 个 V vectors。它不是操作系统的 4 KiB 页面。查看配置源码

交互计算：索引规模与加载预算

假设 head dimension = 128、K/V 都是 BF16、共有 8 个 KV heads。这里只计算有效 KV 数据，不含索引、映射、量化元数据或 tensor parallel 分片。

历史页数8,192
每页 K+V / 单层单 head8 KiB
选中 token 数1,024
读取 / 单层单 head512 KiB
读取 / 单层 8 heads4 MiB
历史覆盖比例0.78%

小页减少读取放大，却增加索引对象、去重和调度成本；大页让索引更小、搬运更连续，却可能为少量重要 token 加载大量无关 KV。比较不同 page size 时，应固定读取字节/token 预算或质量目标，不能固定 Top-k page 数就宣称公平。

token graph → 高分 token IDs → page 映射与去重 → 加载 pages
page graph  → page 代表向量搜索 → page IDs → 加载 pages
层次索引    → 粗粒度 group → 细粒度 pages → attention

单层单 head 每页字节数 = 2 × page_tokens × head_dim × bytes_per_element
完整 KV 字节数 ≈ 2 × layers × KV_heads × head_dim × tokens × bytes

索引粒度、分配粒度、传输粒度和 GPU tile 大小可以不同。若每个 head 独立聚类，必须计入对应索引和映射成本。

05 / IDEAS WORTH KEEPING

讨论中值得保留的观点，以及它们的边界

“检索 token，返回 page”合理，但已有直接先例

IceCache 的算法将检索到的关键 key IDs 映射为 page IDs，再批量加载 pages。差异必须落在搜索成本、页面组织、更新机制或 kernel 执行效率上；仅换成 graph index 不足以建立 novelty。

“像 MoE 的 block routing”已有 MoBA

MoBA 用 block 内 keys 的 mean pooling 与 q 打分，选择 Top-k blocks，再执行块内 attention。CPU 图检索、动态更新和 CXL 路径仍需另行验证，但 block routing 本身不能当成新概念。

随机 scatter 后再建 centroid，需要先证明页具有区分度

随机页随着样本增加可能都接近总体均值。页占用率高不等于 centroid 有用。如果阈值后重新聚类，必须计入 KV 重排、映射切换和旧页回收。

待验证延迟建索引应由“未来检索收益是否超过构建、重排和维护成本”触发，而不是只看 token 数。

centroid 更新便宜，不代表图维护便宜

new_mean = old_mean + (new_key - old_mean) / (count + 1) 是 O(d) 更新，但代表点移动会使邻接边过时。需要比较实时修边、批量修边、冻结满页与 delta buffer。

共同访问不一定等于 key 相近，但 co-activation 已有人研究

RetrievalAttention 已用 query 分布改造图结构；Swarm 已测量共同激活、按共同激活聚类并在线适应。我们仍可验证固定容量页、相同质量预算下，历史轨迹对未来 multi-turn queries 是否能降低总访问字节。

固定 GPU 工作集可以成立，总历史仍可能线性增长

分页降低分配浪费；量化降低每 token 字节数；offloading 改变存放位置；稀疏检索减少每步读取。它们不能互相替代。当前索引方向优化的是活跃工作集和访问路径。

07 / SYSTEMS PAPERS THAT SHAPE THE PROJECT

OSDI / SOSP：不只看方案，也看如何把效率问题做成系统论文

这些论文分成两层：第一层直接定义 KV cache、搬运和 kernel 的基线；第二层帮助我们学习如何隔离瓶颈、设计流水线并证明端到端收益。会议标签本身不是选择理由。

最接近当前核心

Page、选择、搬运与 kernel

PagedAttention（SOSP’23）定义逻辑块到物理块的基础；InfiniGen（OSDI’24）展示预测选择和预取；ECHO（OSDI’26）把 indexer、recall 与 fused kernel 流水化。

2026 前沿边界

数据布局和异构内存已成为主问题

Strata（OSDI’26）指出碎片化布局会制造小 I/O；DirectKV（OSDI’26）直接访问 CPU-resident KV，并融合 KV generation 与 attention。我们的设计必须优于“更好的传输与 kernel”这一强基线。

端到端评测方法

局部优化必须穿过 serving 调度

Sarathi-Serve（OSDI’24）用 chunked prefill 控制干扰；DistServe（OSDI’24）分离 prefill/decode 并以 TTFT、TPOT goodput 评估；Llumnix（OSDI’24）展示如何隐藏 KV 状态迁移。

方法借鉴 · 非直接基线

远端内存与动态 page 粒度

Ditto（SOSP’23）研究分离式内存上的自适应缓存；MEMTIS（SOSP’23）研究动态 page 分类和 page size。它们不回答稀疏 attention，但适合借鉴 metadata 成本、冷热识别和远端访问实验。

建议阅读顺序：PagedAttention → InfiniGen → ECHO → DirectKV / Strata；完成微基准后，再用 Sarathi-Serve、DistServe 和 Llumnix 检查局部收益能否转化为 TPOT、goodput 与尾延迟收益。
08 / EVIDENCE BEFORE NOVELTY

从可复现的多余工作中寻找 novelty

以下是用于筛选研究方向的实验假设，不是已经成立的贡献。

E1 · 搜索

图索引何时才超过扫描？

比较 page 代表扫描、token graph、page graph。覆盖上下文长度、batch size、page size 和并发。统计图节点/边读取，而不是只统计返回的 KV。

否定信号：扫描在有效规模内始终更快，或检索不是端到端热点。

E2 · 更新

检索节省是否被维护成本吃掉？

比较逐 token 插入、批量更新、冻结页 + delta buffer。记录构建、插入、修边、重排和暂停时间，以及延迟更新造成的质量变化。

否定信号：简单批量策略已足够，复杂维护没有净收益。

E3 · 布局

高 token recall 是否仍要读取太多 pages？

比较位置顺序、key 相似聚类和共同访问布局。固定页容量、复制预算和质量目标；用早期 query 构建，后续 query 测试。

否定信号：IceCache 类布局已接近离线上界，或收益被复制/重排抵消。

E4 · Kernel

候选减少为何没有等比加速？

分解去重、gather、DMA、launch、attention 和合并。比较 CPU partial attention 与 GPU page attention，找出真实 break-even point。

否定信号：现成 kernel 已接近硬件上限，没有明显额外工作可消除。

最低限度的测量表

维度必须记录常见误判
质量attention 输出误差、覆盖质量、长任务最终准确率只报告 ANN recall
检索p50/p95/p99、访问节点/边、索引容量、CPU 时间忽略 q 传输和 page 去重
更新均摊/尾部插入、重排字节、建索引时间只报告 steady state
数据路径索引 + K + V 实际读取、传输和 GPU idle只数返回 KV
端到端TTFT、TPOT、吞吐、实际重叠率kernel 更快等于 serving 更快
有说服力的贡献链：可复现的多余工作 → 已有机制为何难以避免 → 针对性的索引/布局/kernel 改动 → 相同质量下的端到端收益。
09 / BUILD THE MEASURABLE PATH

原型路线：先隔离热点，再接入 serving

  1. Python trace replay：采集 Q/K/V 和 oracle attention 轨迹，验证 page selection 的质量与理论读取量。
  2. C++ CPU microbenchmark：实现或接入 SIMD 扫描、图搜索、批量插入和 page 去重。
  3. GPU kernel microbenchmark：复用 paged attention；只针对 profiling 找到的 gather、变长处理或融合热点写 CUDA/Triton。
  4. 端到端集成：Nano-vLLM 用于理解；正式原型优先接入 vLLM 或直接基线，观察调度和同步是否抵消收益。
  5. CXL 对照：比较索引全在 DRAM、全在 CXL、热导航结构在 DRAM 的混合放置；KV 数据单独作为实验变量。

Nano-vLLM · vLLM · IceCache · FlashInfer

CXL 是独立实验变量。“索引放 CXL”和“KV 放 CXL”是不同问题；SAC 已覆盖 sparse KV 的 CXL 数据路径。
